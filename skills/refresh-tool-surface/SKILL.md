# refresh-tool-surface

Regenerates this repo's agent-facing description of its own tool — the command
reference a skill, README or MCP description hands to an agent — from what the
tool actually reports, and tells the user what changed. At the end they get a
diff of the surface, not a claim that it is up to date.

A hand-maintained reference is wrong from the first flag that changes, and wrong
invisibly: the agent obeys the document, the tool rejects the call, and the
failure reads as the agent's mistake.

---

## Step 1 — Find the reference and its source

Locate two things before changing anything:

- **The reference**: the file describing the tool's commands to an agent. Look
  for a skill under `skills/`, `.agents/skills/` or `.claude/skills/`, an MCP
  tool description, or a commands section in `AGENTS.md` / `README.md`.
- **The generator**: the tool's own way of reporting its surface — a
  `dump-help` / `--help` command, a schema dump, an MCP `tools/list`.

If the tool has no such command, stop and say so. The fix is to add one; a
reference re-typed by hand is the thing this skill exists to remove. Report that
as the finding rather than hand-writing the reference anyway.

If the reference is already generated by a script the repo owns, run that script
and skip to Step 3.

---

## Step 2 — Regenerate from the tool

Build the tool from the current working tree first — a reference generated from
a stale binary documents the previous change, and looks identical to a correct
one.

Then capture its surface output and write the reference from that capture only.
Do not merge in remembered flags, and do not keep an entry because it looks
useful: if the tool no longer reports it, it is gone.

If the tool cannot build or the surface command fails, stop and report that.
A reference regenerated from a failed run is worse than a stale one, because it
is confidently empty.

---

## Step 3 — Report what moved

Diff the regenerated reference against the committed one and say, in the final
message:

- commands and flags **added**
- commands and flags **removed or renamed** — these are the breaking ones; call
  them out first
- anything the tool reports that the reference cannot express (interactive-only
  commands, undocumented flags)

If nothing changed, say that plainly. "Already current" is a real result and the
common one.

---

## Step 4 — Flag the guardrail if it is missing

If nothing in the repo fails when the reference goes stale, say so once, and
name the check: a test that runs the tool's surface command and compares it with
the committed reference. Do not build it unasked — flag it and let the user
decide.

---

## Notes

- Regenerate in the *same change* that alters the surface. A follow-up commit is
  a window in which every agent reading the reference is being misled.
- The reference is for a caller that cannot ask questions: prefer exact command
  spellings and required arguments over prose about intent.
- This skill changes generated content only. If the tool's surface looks wrong,
  that is a defect in the tool — report it, do not paper over it in the
  reference.
